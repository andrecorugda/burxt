# Burxt — A4.6 Interfaces & Dispatch Specification

> Status: **spec, to implement.** This adds interfaces (traits) and dynamic
> dispatch on top of the A4.5 aggregate ABI and v0.0.13 methods. It is the slice
> where the A4.5 layout guarantee ("no hidden header, ever") finally gets *used*.
>
> **This spec is written defensively on purpose.** A4.5 was constrained by physics
> — memory layout has right answers the machine enforces. A4.6 is constrained only
> by judgment: nothing in the hardware says "no" to interface inheritance, default
> methods, or generic bounds. Object-oriented scope creep enters languages *exactly
> here*. So the "must NOT do" section (§6) and the deferred ledger (§7) are not
> footnotes — they are the load-bearing part of this document. Read them first if
> you read nothing else.

---

## 0. The governing tension (why this spec is strict)

Every feature below is *individually* defensible and *collectively* a swamp. The
history of OOP type systems is a graveyard of languages that added default methods,
then interface inheritance, then associated types, then generic bounds, then
variance rules — each a reasonable step, the sum an edifice you need a book to
understand. Burxt's North Star says: **pick a few signature features, resist the
kitchen sink.** For A4.6 that means: ship the *smallest* interface system that lets
one type stand in for another behind a contract, and defer everything else with a
written reason. A feature enters A4.6 only if a concrete, required program cannot be
written without it — the same bar the expression-statement feature had to clear in
v0.0.13.

---

## 1. What an interface IS in Burxt — the minimal model

A **trait** is a named set of method signatures a type can promise to satisfy. That
is the whole concept. Concretely:

```burxt
trait HasBalance {
    fn balance_of(self) -> Decimal<2>
}

// A struct satisfies a trait by implementing its methods with matching receivers.
impl HasBalance for Account {
    fn (self: Account) balance_of() -> Decimal<2> { return self.balance; }
}
```

Rules that define the minimal model:

- A trait declares **method signatures only** — name, receiver form, params, return
  type. No fields. No state. (Interface Segregation from the North Star: keep them
  small; a trait with one method is the healthy default, not a code smell.)
- A type satisfies a trait via an explicit `impl Trait for Type` block. **Explicit,
  not structural** — Burxt does not auto-satisfy a trait just because the method
  shapes happen to match (that is Go's structural typing; we choose nominal so
  satisfaction is a deliberate, greppable declaration, and so adding a trait method
  later doesn't silently un-satisfy types that never opted in).
- The `impl` reuses the v0.0.13 method machinery unchanged: receivers are still
  `self: T` (byval) or `mut self: T` (by-address). A trait method is just a method
  that also counts toward a contract. **No new receiver mechanics.**
- Trait methods obey the same mutability inheritance as v0.0.13: a `mut self` trait
  method requires a `let mut` binding on a plain variable. Nothing new to design.

## 2. Resolution — static wherever possible, dynamic only when asked

This is the single most important design decision in A4.6, and it is: **static
dispatch is the default; dynamic dispatch happens only through an explicit trait
object.** Two distinct call paths, and the programmer chooses by how they write the
type, never by accident.

### 2a. Static dispatch (the default — zero new runtime cost)

When the concrete type is known at compile time, a trait-method call resolves
*statically*, exactly like a v0.0.13 method call. `acct.balance_of()` where `acct:
Account` compiles to a direct call. The trait is a *compile-time constraint* here,
not a runtime mechanism. No vtable, no indirection, no fat pointer. This is the
common case and it must stay as cheap as a plain method call.

### 2b. Dynamic dispatch (opt-in, via an explicit trait object)

When you want one variable to hold *any* type satisfying a trait and dispatch at
runtime, you write an explicit **trait object**. Proposed surface syntax (bikeshed
allowed, semantics fixed):

```burxt
let acct: dyn HasBalance = some_account;   // `dyn` = "any type satisfying it"
print(acct.balance_of());                  // dispatched at runtime via vtable
```

- `dyn Trait` is the *only* thing that triggers dynamic dispatch. If you never write
  `dyn`, you never pay for a vtable. Explicitness is the whole discipline.
- **This is where A4.5's guarantee is spent.** A `dyn Trait` value is a **fat
  pointer**: `(data pointer, vtable pointer)`. The vtable lives *outside* the object,
  in static read-only data. Because A4.5 mandated "layout == declared fields, no
  hidden header," the data pointer points at pure field data — becoming a trait
  object does not move a single field, and a struct's layout is identical whether or
  not it's ever used as `dyn`. That invariant is now cashed in. Verify it: a struct's
  field offsets must be byte-identical in a direct-call context and a `dyn` context.

### 2c. Why this split, stated honestly

Rust made exactly this choice (`impl Trait`/generics = static, `dyn Trait` =
dynamic) and it is widely considered one of its best decisions: you get zero-cost
abstraction by default and pay for runtime polymorphism only when you ask by name.
It fits Burxt's "no hidden costs / strict silently" ethos precisely. The cost is one
concept the programmer must learn (`dyn`), which is a small, honest price for making
performance legible in the syntax.

## 3. The vtable — concrete shape (this is the only genuinely new machinery)

A trait object's vtable is a static, immutable table of function pointers, one per
trait method, in trait-declaration order.

- One vtable is emitted **per (Type, Trait) pair** that is actually used as `dyn`.
  If a type never becomes a trait object, no vtable is emitted for it (pay for what
  you use).
- The vtable is read-only static data, shared by all trait objects of that
  (Type, Trait) — not per-instance. The *instance* carries only the two pointers.
- Method lookup is: index into the vtable by the method's fixed slot (known at
  compile time from trait-declaration order), call the function pointer, pass the
  data pointer as the receiver.
- Receiver passing through the vtable obeys A4.5/§1 unchanged: a `self: T` trait
  method still gets a value copy (the callee copies from the data pointer); a
  `mut self: T` trait method operates on the data pointer as real storage. The fat
  pointer's data half *is* the caller's storage for the mut case — same rule as
  direct methods, no new aliasing surface.

That is the entire runtime addition: a per-(type,trait) static table and a two-word
value. Nothing else.

## 4. Interaction with existing features (must all still hold)

- **Method namespacing (v0.0.13):** methods stay namespaced by (receiver, name).
  A trait `impl` registers its methods against the concrete type; static calls
  resolve by the base type exactly as today. No change to namespacing.
- **Value semantics (A4.5 §1):** passing a `dyn Trait` is passing a two-word value
  (copy the two pointers). Passing a concrete type is unchanged. The §1
  mechanism-switch test must be extended to cover a call made statically vs. the same
  call made through `dyn` — observable behavior must be identical.
- **Correctness family:** a `dyn Trait` is a real, non-null value — there is no
  "null trait object." Absence of a trait object is `Option<dyn Trait>`, forced-
  handled like any other optional. Null-dispatch (the classic NPE) is impossible by
  construction.
- **Exhaustiveness:** unaffected here; it becomes relevant only if/when Burxt adds
  sum types with trait bounds, which is deferred (§7).

## 5. What A4.6 must deliver (implementation checklist, dependency-ordered)

1. **Trait declaration:** parse `trait Name { <sig>* }`; store the method signature
   set (name, receiver form, params, return).
2. **impl block:** parse `impl Trait for Type { <method>* }`; typecheck that the
   methods exactly satisfy the trait's signatures (all present, receivers and types
   matching) — a partial or mismatched impl is a compile error naming the missing/
   wrong method.
3. **Static trait calls:** a trait-method call on a known concrete type resolves to a
   direct call (reuse v0.0.13 path). No vtable emitted.
4. **`dyn Trait` type:** parse it; represent it as the two-word fat pointer in the
   type system and in codegen.
5. **vtable emission:** per (Type, Trait) used as `dyn`, emit the static function-
   pointer table in trait-declaration slot order.
6. **Dynamic call lowering:** a call on a `dyn Trait` loads the slot's function
   pointer from the vtable and calls it with the data pointer as receiver, honoring
   A4.5 receiver rules.
7. **Tests (the product — weight these heaviest):**
   - static trait call compiles to a direct call (no vtable in output);
   - `dyn` dispatch calls the correct impl at runtime across ≥2 types;
   - **field offsets identical in direct vs. `dyn` context** (A4.5 guarantee cashed);
   - value semantics preserved through `dyn` (mechanism-switch test extended);
   - `Option<dyn Trait>` forces handling; no null trait object;
   - **rejections:** incomplete impl; impl with wrong receiver/signature; calling a
     `mut self` trait method on an immutable binding; using a type as `dyn Trait` it
     doesn't impl. Each rejection reads as English advice.

## 6. What A4.6 must NOT do (the load-bearing section)

Each of these is a real feature other languages have. Each is **deferred, not
rejected forever** — but none enters A4.6, because none is *required* to make one
type stand in for another behind a contract. Adding any of them here would be the
kitchen sink the North Star forbids.

- **NO default methods** (methods with bodies in the trait). Tempting and common, but
  they pull in override-resolution rules and the question "which body runs." Defer
  until a required program needs shared default behavior. (§7)
- **NO interface/trait inheritance** (`trait A : B`). This is the single biggest
  complexity multiplier — it turns trait satisfaction into a graph problem. Defer
  hard. (§7)
- **NO generics / generic trait bounds** (`fn f<T: Trait>(x: T)`). Generics are a
  whole milestone of their own with inference, monomorphization, and bound-checking.
  A4.6 is dynamic dispatch via `dyn` only; static polymorphism over type parameters
  is out. (§7)
- **NO associated types or associated constants** in traits. Signatures only.
- **NO blanket impls** (`impl Trait for all T where ...`). No conditional/overlapping
  impls. One explicit `impl Trait for ConcreteType` at a time.
- **NO trait objects with generic methods** (object-safety edge cases). If a trait
  method were generic it couldn't go in a vtable; since generics are out entirely,
  this can't arise — keep it that way.
- **NO auto-derive / structural satisfaction.** Nominal only (§1): satisfaction is an
  explicit `impl`, never inferred from method-shape matching.
- **NO operator-overloading-via-traits** (the `Add` trait pattern). Arithmetic stays
  built-in per the numeric core; do not let traits become the operator backdoor.
- **NO multiple dispatch.** Dispatch is on the single receiver only.
- **NO downcasting / runtime type reflection** (`as`, `is`, `Any`). A trait object
  exposes its trait methods and nothing else; you cannot ask "what concrete type is
  this really." Reflection is a large, separate, mostly-undesired surface.

If implementing A4.6 seems to *require* one of these, stop and record why in the
ledger — that is real signal about the design, not license to add it silently.

## 7. Deferred-features ledger (append to DESIGN.md; the audit trail)

Each entry: the feature, why it's deferred, and the concrete trigger that would earn
it a future milestone. This is how the design phases stay honest without physical
constraints to enforce them.

| Feature | Why deferred | Earns its place when… |
|---|---|---|
| Default methods | Adds override-resolution rules | A required program needs shared default behavior across many impls |
| Trait inheritance | Turns satisfaction into a graph problem | A real hierarchy genuinely can't be modeled by small separate traits |
| Generics / bounds | Whole milestone: inference, monomorphization | Static polymorphism over type params is concretely needed (own phase) |
| Associated types | Compounds generics complexity | Only alongside generics, if ever |
| Blanket/overlapping impls | Coherence + overlap rules | A required pattern can't be expressed one-impl-at-a-time |
| Operator traits | Backdoors operator overloading | Never, unless the numeric-core stance is deliberately revisited |
| Downcast / reflection | Large surface, breaks abstraction | A required program genuinely needs runtime type identity |

These join the existing interim/superseded ledger (512 MB compile stack → iterative
AST walkers; scale-18 ceiling; sret-over-register-pair; declaration-order layout).

---

## 8. The one-line identity check

A4.6 succeeds if: **a type can promise to satisfy a small named contract, callers
get that contract statically for free and dynamically only when they write `dyn`,
the vtable lives outside the value so layout never changes, and every deferred
feature is written down with a trigger rather than silently added.**

If at the end you can say all of that is true and the "must NOT do" list is still
intact, the milestone held the line. If two or three deferred features crept in
"because they were easy," the discipline failed even if the tests are green — because
in this phase, scope *is* the thing being tested.
