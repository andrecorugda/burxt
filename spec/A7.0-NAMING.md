# Burxt — one word per concept

> Status: **in force, and tested.** `one_word_per_concept_in_the_burxt_compiler` in
> `tests/runner.rs` enforces the parts of this that can be checked mechanically.

## Why this document exists

Andre, 2026-07-29, after asking whether a function was called `find_sym` or `find_bind`:

> "please do audit, we keep on repeating this kind of inconsistent"

He was right that it kept recurring, and the audit found why. **The convention already existed.**
Four of six lookup families already followed it. Nobody had written it down, so the other two drifted
and nothing noticed.

## The rule

A concept gets **one word**, used everywhere it appears:

| | |
|---|---|
| the lookup | `find_<thing>` |
| the array it searches | `<thing>s` |
| the record it holds | `<Thing>` |
| its counter, if it has one | `find_<thing>_calls` |

```
find_method    → methods    → Method       ✅
find_slot      → slots      → Slot         ✅
find_instance  → instances  → Instance     ✅
find_type      → types      → TypeDeclaration
find_binding   → bindings   → Binding      ✅ since v0.0.122
find_function  → functions  → DeclaredFunction  ✅ since v0.0.122
```

## What the audit found

**`find_sym` searched `self.syms`, which held `Binding` records, and incremented
`find_binding_calls`.** Four names for one concept, in one function, three of them visible in a
five-line body:

```burxt
function (mutable self: Unit) find_sym(src: String, start: Int, length: Int) -> Int {
    self.find_binding_calls += 1;
    ...
        if spans_equal(src, self.syms[i].start, ...
```

And `find_fun` searched `self.funs` while its counter said `function` and its record was
`DeclaredFunction` — so `fun` and `function` both meant function, in adjacent lines.

**`Binding` won** over `sym`/`symbol`, and not by coin toss. It is what the thing *is*: a name bound
to a type in a scope. And "symbol" is already taken — the emitter uses it for a **linker** symbol,
which is a different thing entirely. A word that means two things in one codebase is worse than a
word nobody likes.

**Clipped fields**, all of them now spelled out: `name_len` → `name_length`, `params` →
`parameters`, `pos` → `position`, `receiver_len` → `receiver_length`, `type_params` →
`type_parameters`, `instance_args` → `instance_arguments`.

## Where the rule stops, deliberately

**Fields and functions must use the whole word. Short-lived locals need not.**

A field crosses files, so an abbreviation in one costs every reader who meets it somewhere else. A
local named `sig` inside a twelve-line function has its declaration on screen with its use, and a
rule reaching that far is a rule people route around. `let sig: Node = self.nodes[item.c];` stays.

Two words are the real words in this language and are not clips: **`len`**, which is the builtin, and
**`ptr`**, which is what a pointer is called in the LLVM IR this compiler emits.

## What the test checks, and what it cannot

**Checks:** that every one of the six families still has its `find_<thing>`; that the six clipped
spellings the audit removed have not returned; that no field in `types.bx` is a clipped word or ends
in one.

**Cannot check:** whether a *new* concept picked a good word. That is a judgement, and the test
would have to know what the concept is. What it does instead is make the existing families
unbreakable, so drift has to start somewhere new rather than eroding what is already right.

It also cannot see prose or emitted IR, and does not try — comments and string literals are stripped
before it looks. The IR in `emit.bx` is full of `%tmp` and `ptr` because that is LLVM's language, not
Burxt's.

## Stage-0, and where the line fell there (v0.0.123)

Rust was audited separately, and the numbers split the question cleanly. Identifier counts, with
comments and string literals excluded:

| | clipped | full word | verdict |
|---|---|---|---|
| `ty` | 361 | 0 | **left alone** — uniform, and idiomatic in Rust compilers |
| `ret` | 118 | 0 | **left alone** — uniform |
| `params` | 135 | 34 | mixed → **`parameters`** |
| `args` | 211 | 41 | mixed → **`arguments`** |
| `sig` | 32 | 27 | mixed → **`signature`** |
| `toks` | 11 | 15 | mixed → **`tokens`** |

**Mixed spellings are the bug; terse-but-uniform is a preference.** `ty` used 361 times and
`the_type` never is not the disease this document is about — it is a house style, and one that reads
normally to anyone who has seen rustc. `params` used 135 times beside `parameters` 34 times is two
words for one concept, which is the disease exactly.

So `ty` and `ret` stay. That is a deliberate stopping point rather than an oversight, and it is
recorded so nobody has to guess whether the sweep ran out of energy.

Three names are protected and must never be renamed: `std::env::args()`, `Command::args()`, and the
LSP wire key `"params"`. The first two are other people's APIs; the third is a protocol.

## A rename by text is only as good as its string-skipping

This sweep skipped string literals by scanning for quotes and counting them. It broke once, in
`src/rust-compiler/json.rs`, on a line above a **raw string**:

```rust
let msg = r#"{"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}}"#;
```

Those internal quotes desynchronised the parity, so the scanner thought it was outside a string by
the time it reached `"params"` on the next line — and renamed an **LSP protocol key**. The test
caught it immediately, which is the only reason it is a footnote rather than a broken editor.

That is the **fifth** time in one project that a word-boundary rename has gone wrong in a new way:

1. `\nfn` is not a word boundary, so five inline programs were missed
2. `\barg\b` matched `Command::arg()` — 129 sites, 54 build errors
3. `'"'` is not a string, and a naive scanner corrupted `json.rs` and `diag.rs`
4. `Result.Err` matched inside the already-renamed `Result.Error`, giving `Result.Erroror`
5. a raw string's quotes desynchronised a string-skipping scan, in `json.rs` again

**A sixth, found while writing this list.** The two items above arrived corrupted. The script
that wrote this file used a shell heredoc, which turned `\n` into a real newline — splitting
item 1 across two lines — and each `\b` into a literal backspace byte, so item 2 lost the very
word boundaries it was about. A document warning about escaping was corrupted by escaping,
while being written, and the first attempt to repair it failed too because the repair script
had the same bug.

The same rule catches it one layer up: **the tool writing the text is another language the
text passes through.** A heredoc is not a neutral pipe.

The rule that covers all six, and the one to check before any future sweep:

> **A textual rename is safe only when the word cannot occur in any OTHER language the file
> contains** — and a Rust file contains Rust, raw strings, error messages, LSP keys, and often
> emitted LLVM IR. Rename declarations first and let the compiler find the uses; when that is not
> possible, verify the count before and after, and read every diff that lands inside quotes.

## A seventh failure: an end-of-line anchor misses a one-line body (v0.0.145)

Removing `allocates` from ~200 signatures, the sweep matched the marker only where it ended the
line — either as the last token or immediately before a `{` that closed the line:

```python
re.compile(r" allocates(?=\s*\{\s*$|\s*$)")
```

Narrow on purpose, so `flag_allocates` and `expr_allocates_calls` could not match. It reported
zero changes in `tests/pass/implement_receiver_shorthand.bx` and was believed, because zero is a
plausible answer for a file that might simply not use the word.

It uses it twice:

```burxt
function (self) label() -> String allocates { return "book: " + self.title; }
```

The `{` is there, and so is the rest of the body. Four sites in two files, found only by grepping
`" allocates {.\+"` afterwards — that is, by asking the opposite question.

**The lesson is not "add `.\+` to the pattern".** It is that a sweep reporting *no* changes in a
file is a claim, and an unverified one. Every count a sweep prints should be checked against a
search for what it did *not* match, because a pattern that is too narrow fails silently while a
pattern that is too wide fails loudly.

**The sweep this page had missed entirely, until v0.0.214: DIRECTORIES.** The self-hosted compiler lived
in `examples/burxt/` — a working compiler, and this project's capability certificate, under a name that
says "sample code." Every rule here had been applied to keywords and functions and none of it to paths.
Both compilers now sit at `src/rust-compiler/` and `src/burxt-compiler/`, named by the language each is
written in.

It produced an **eighth** failure mode, and it is the seventh's shape exactly. The sweep replaced
`examples/burxt/` *with a trailing slash*, so `collect_bx(root.join("examples/burxt"))` in
`tests/runner.rs` survived it — and `scripts/site-reference.py` survived it too, because it
**constructs** its paths (`read("src", "lexer.rs")`) rather than spelling them out. **A textual sweep
cannot see a path that is assembled.** What caught both: after the sweep, walking every code and config
file and asserting that *every cited path exists*. That check belongs in the sweep, not after the tests
fail.

The next sweep here is `region`, and
`region r { print(x); }` is the same shape on one line.

## A ninth failure: a name DERIVED by a tool (v0.0.215)

`src/burxt-compiler/stage1.bx` became **`main.bx`**, because every neighbour is named for what it does
— `parser.bx`, `check.bx`, `emit.bx` — and the entry point alone was named for its position in a
bootstrap sequence that no longer exists. A maintainer asks *where does the program start*, and the
answer is spelled `main` in every language, including in `src/rust-compiler/main.rs` at the same place
doing the same job.

The sweep replaced all **55** occurrences of the string across seventeen files, left no leftovers, and
**still broke three tests.** The reason is a failure mode none of the eight above covers:

> **`burxt build path.bx` with no `-o` DERIVES the binary's name from the filename.** So `stage1.bx`
> produced a binary called `stage1`, and three tests ran `scratch.join("stage1")`. That string is not a
> path, not a filename, and not the renamed thing — it is the *output of a naming rule applied to* the
> renamed thing. Grep found it and it told me nothing: `scratch.join("stage1")` reads exactly like an
> arbitrary scratch name, and the eight other tests in the file that write `let stage1 =
> scratch.join("stage1")` **beside an explicit `-o`** are genuinely arbitrary. Nothing in the line
> distinguishes the two.

**A derived name is a reference no sweep can see**, and the eighth failure is its cousin rather than its
equal: an *assembled path* (`read("src", "lexer.rs")`) at least contains the fragments, so a smarter
grep reaches it. A derived name contains no fragment of the source at all — the connection lives only
inside the tool that derived it.

**The fix is not a better sweep. It is to stop deriving.** Those three builds now pass `-o` explicitly,
so the name is written down where a sweep can find it, and the derivation is gone rather than
documented. That generalises: **before renaming a file, ask what reads its name without being told it**
— a default output path, a test discovering fixtures by stem, a module resolved from its filename, an
artifact named after its input.

The eighth failure's check — *after the sweep, assert every cited path exists* — would not have caught
this one, because `scratch.join("stage1")` cites no path that ever existed on disk before the test ran
it. What caught it was **running the whole suite**, which is the only instrument that sees a name a tool
invented. Three tests failed within ninety seconds. That is the check, and it is the one already in
place.

## A tenth failure: a directory invented beside the one that already existed (v0.0.216)

Andre, in the middle of the diagnostics work: *"see if I did not mention, you are just creating trash
unorganized language files."*

Fair, and it had just happened again in the same turn. `diag.bx` needed a driver program — a Burxt
program a runner invariant supplies arguments to, which is neither a `tests/pass/` fixture (whose answer
is a checked-in `.stdout`) nor a `tests/fail/` one. So I created **`tests/tools/`** and put it there.

**`tests/support/` already existed, holding `failing_suite.bx`, for exactly that reason.** I did not look.

This is the shape of the other nine failures, one level up: they are all about a name that no longer
describes its subject, and this is about a name invented while a correct one was already in use. And it
is worth admitting what the ratio says — of the three layout defects fixed in three versions, **two were
found by Andre and one by a test.** The compiler filed under `examples/` (v0.0.214) and `stage1.bx`
(v0.0.215) were both read off the directory listing by a human. Every rule in this document had been
applied to identifiers and none of it to the tree they live in, because **nothing in the suite ever
looked at the tree.** A claim about behaviour gets measured here; a claim about organisation was taken on
trust.

So `the_repository_layout_is_declared` now names every directory and what belongs in it, and a new one
fails the suite until it is either justified in that list or recognised as a duplicate of an existing
home. That is the same instrument as the rest of this document — *if it is worth fixing twice, it is
worth a test* — pointed at the one thing it had never been pointed at.

**The rule that would have prevented it, stated for the next time:** before creating a directory, list
the siblings and read what they hold. A new home is a claim that no existing one fits, and that claim is
almost always wrong.

## The lesson worth keeping

**An audit finds a thing once.** The `find_sym` inconsistency survived because every reader who met
it was busy with something else, and there was no statement to measure it against. The fix that
matters is not the rename — it is the eleven lines of test that make the rename permanent.

The same shape as `spec/M9-PERFORMANCE.md`'s ratchets and the keyword-currency check in
`the_guide_and_examples_are_linked_and_compile`: **if it is worth fixing twice, it is worth a test
the second time.**
