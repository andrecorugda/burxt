# Burxt — Record update (A8.0)

> Status: **spec, to implement.** Raised by Andre on reading `examples/classes.bx`:
>
> > *"inside class function, why do you need to return `Account { owner: self.owner, balance: self.balance - amount }`? You are already inside `Account` — why not use `self`?"*
>
> Andre's later steers are recorded in **§5a** (accessors bounded by contracts) and **§5b**
> (`__construct`, and no redundant class name inside its own class). §5b names the defect more
> precisely than §2 did — `Account` appears THREE times inside `class Account` — and settles the
> question §5a left open: the constructor is the door, accessors are the rules, and `with` is what
> keeps either from re-introducing the transposition bug.
> The answer turned out to be better than "convenience", which is why this is a spec and not a
> papercut row. **The explicit re-construction is where a silent wrong answer lives**, and that is a
> thesis-level argument rather than an ergonomic one.

## 1. The question, and what already answers part of it

The example that prompted it:

```burxt
function (self: Account) withdraw(amount: Decimal<2>) -> Account
    requires amount > $0.00
    requires amount <= self.balance
{ return Account { owner: self.owner, balance: self.balance - amount }; }
```

Two fields, one of which changes, and the unchanged one is copied by hand.

**Part of the question already has an answer, and it is worth separating out.** Burxt has
`function (mutable self: T)` since v0.0.201 — `tests/pass/method_mutating.bx` — so this *can* be
written as mutation:

```burxt
function (mutable self: Account) withdraw(amount: Decimal<2>) -> Int { self.balance -= amount; return 0; }
```

The example does not, deliberately. A value-returning `withdraw` leaves the old `Account` intact, so
a contract can say `ensures result.balance == old(self.balance) - amount`, and `ada.withdraw($30.00)`
does not destroy `ada`. **For money that is the better default**, and the choice is not what this
spec changes. What it changes is the cost of *writing* it.

## 2. Why this is a correctness question, not a verbosity one

Measured, v0.0.230, on the compiler as it stands:

```burxt
class Person { first: String, last: String }
function (self: Person) renamed(to: String) -> Person {
    return Person { first: self.last, last: self.first };   // transposed
}
```

**Compiles with no diagnostic, and prints `Lovelace` where `Ada` was meant.** Both fields are
`String`, so nothing in the type system can see it. There is no rule to add, either — the program is
well-typed, and `Person { first: self.last, ... }` is a thing a caller might legitimately want.

Now scale it. A nine-field record whose method changes one field is **eight hand-copied assignments,
every one an opportunity to transpose two fields of the same type**, and the reviewer's job is to
diff two lists of nine to find the one line that differs. `DESIGN.md`'s bar is *"strict enough that
an agent cannot make a costly mistake, and plain enough that a reviewer can see that it didn't."*
The hand-copy fails both halves at once: it hands the writer eight chances to err, and it hides the
one line that matters inside eight that look identical.

> **The point is not that the copy is tedious. It is that the copy is the only place in the language
> where a silent field transposition is both possible and invisible** — and it appears in exactly the
> style this language recommends for money.

A record-update form makes that class of bug **unrepresentable**, because the unchanged fields are
never named:

```burxt
return self with { balance: self.balance - amount };
```

## 3. The decision — `with`, spelled as a word

```burxt
<expression> with { field: value, ... }
```

- The left side is any expression of a record type, not only `self`. `other with { ... }` is the same
  operation and refusing it would be an arbitrary rule.
- The result is a **new value**. Nothing mutates; `with` is not a shortcut for `mutable self`.
- Fields not named keep the value they had in the left-hand expression.

**Why a word and not `{ ..self }` or `{ ...self }`.** The same call `divide_floor` and
`shift_right_zeros` already record: a symbol has to be memorised, a word can be read. `..` in
particular would be the first appearance of that token in the language and would arrive with no
precedent to lean on. `with` also reads in the direction the code runs — *this value, with this
changed* — which is what a reviewer is trying to establish.

**Why not a method (`self.with(...)`).** A method takes values, and this takes **field names**. It
is the same reason a record literal is syntax rather than a call.

## 4. The rules, and each one's reason

1. **Every named field must exist on the type.** A typo is a refusal, not a new field.
2. **Each field named at most once.** Two values for one field has no meaning; picking either is a
   guess.
3. **`with { }` — empty — is refused.** It answers a copy of the left side, which is what the left
   side already is, so it is dead syntax that reads as intent. A reader who meets it has to ask what
   was meant, and the answer is never "nothing".
4. **Privacy is unchanged.** A `private` field may be named only where a record literal could name
   it — inside the type's own `class` block. `with` is not a hole in privacy; it is the same rule
   arriving in a second place, and stating that here is cheaper than discovering it later.
5. **Types are checked per field, exactly as in a literal**, including the contract rule that a
   `Decimal` may GAIN a rounding contract and never lose one.
6. **A class invariant, when the class has one, is checked on the result.** This is the mitigation
   for §5's cost, and it is why the two features belong in the same sentence.

## 5. The cost, stated before it is paid

**`with` makes "unchanged" implicit, and the explicit form makes it explicit. That is a real trade
and it does not go away.**

Add a tenth field to `Account` and every hand-written literal **breaks**, forcing the author to
decide what the new field should be in each place. Every `with` silently carries the new field
forward. Usually that is right — a "copy with one change" wants the rest carried — but where the new
field must be *derived* from the changed one, `with` will quietly be wrong and nothing will say so.

Three things make that acceptable rather than merely tolerable:

- **The bug it removes is silent; the bug it introduces is not, when the class has an invariant.** A
  transposed copy produces a plausible wrong answer forever. A carried-forward field that should have
  been recomputed usually violates the class's own stated rule, and rule 6 catches it at the point of
  construction.
- **The explicit form remains.** `with` is an addition. Where every field genuinely must be
  re-decided on every construction, write the literal — and that is now a *choice a reader can see*
  rather than the only option.
- **It is the smaller of two implicit things.** The hand-copy is not explicit about intent either: it
  says `owner: self.owner` without saying whether that is a decision or a transcription. `with` says
  which fields are decisions.

## 5a. Andre's steer: accessors with contracts, which may be the better answer

> *"I think the cleaner approach with this is through getter and setter that is also bounded with
> contracts if needed."*

**Recorded before implementation, because it may replace §3 rather than complement it**, and the
argument for it is stronger than it first looks.

`with` moves a value; an accessor moves a *rule*. Compare what each can say:

```burxt
// §3: the caller states the new value, and the class states nothing.
return self with { balance: self.balance - amount };

// 5a: the class owns the transition, and the contract travels with it.
function (self: Account) set_balance(to: Decimal<2>) -> Account
    requires to >= $0.00
{ ... }
```

Under §3 the invariant is checked **after** the fact (rule 6) and the diagnostic points at the
construction. Under 5a the precondition is checked **at the call**, named, and it appears in the
signature — so `burxt mcp-schema` derives it, `burxt review` sees it change, and the language server
shows it on hover. **None of that is true of a `with` clause**, because a `with` is an expression and
a contract lives on a signature. That is the real difference, and it is not a style preference: the
whole machinery this project has built for making promises visible attaches to signatures.

The cost, equally plainly:

- **It does not remove the transposition hazard, it relocates it.** `set_balance` still has to
  construct the record, so the eight hand-copied fields move *inside* the class. Fewer places, and
  written once by the type's author rather than at every call — better, but not eliminated. §3 and 5a
  compose here: an accessor whose body uses `with` has both properties.
- **A setter per field is a lot of signatures**, and a class with nine fields does not want nine of
  them. So the question 5a really asks is whether accessors should be *generated* with contracts
  attachable, or written by hand — and generated accessors with hand-written contracts is a third
  design, not a smaller one.
- **A setter that returns a new value is not what "setter" usually means.** In a language with no
  mutation-by-default the word carries the wrong expectation, and `with_balance` or `balance_set_to`
  may be the honest name. Naming this is part of the work, not after it.

**Open, and to be decided when this is built rather than now:** whether 5a subsumes §3, whether §3 is
the primitive that accessors are written in terms of, or whether only 5a ships and the transposition
hazard is accepted inside class bodies where the author can see all the fields at once.

## 5b. Andre's fuller shape: `__construct`, and no redundant class name inside its own class

> *"Make sure the class getter/setter/`__construct` will solve the issue of class flexibility and no
> redundant call of class name inside its own class."*

This names the **actual** defect more precisely than §2 did, and the two halves are separable.

### The redundancy is not just the fields — it is the NAME

Look again at what a method inside `Account` has to write today:

```burxt
function (self: Account) withdraw(amount: Decimal<2>) -> Account
{ return Account { owner: self.owner, balance: self.balance - amount }; }
```

`Account` appears **three times inside `class Account`**: on the receiver, on the return type, and on
the constructed value. A reader learns nothing from any of the three, and a rename of the class has to
touch all of them — which `spec/A7.0-NAMING.md` has now recorded **four** name-rot failures about.

Three things follow, and only the third is `with`:

1. **`function (self)` should not need the type inside the class body.** It is refused today —
   *"`function (self)` needs the type: outside an `implement` block nothing says which one"* — and
   inside `class Account { ... }` something does say which one. Measured, v0.0.237.
2. **The return type could default to the enclosing class** where it is the class. Less certain: an
   explicit return type is a promise a reviewer reads, and this language has consistently chosen the
   written promise. Recorded as a question, not a decision.
3. **The construction should not repeat the class name.** `__construct` is Andre's answer, and it is a
   different one from §3's `with`.

### What `__construct` buys that `with` does not

A constructor is a **named place where the class's own rules live**, and both accessors (§5a) and
`with` (§3) are then written in terms of it rather than around it:

```burxt
class Account {
    owner: String,
    private balance: Decimal<2>,

    function __construct(owner: String, balance: Decimal<2>)
        requires balance >= $0.00
    { ... }

    function (self) withdraw(amount: Decimal<2>) -> Account
        requires amount <= self.balance
    { return __construct(self.owner, self.balance - amount); }
}
```

- **Every path into the type goes through one door**, so the invariant is checked once, in one place,
  rather than at each construction site.
- **The class name disappears from its own body**, which is the redundancy Andre named.
- **A `private` field stops being a special case.** Today `Account { balance: ... }` is legal inside
  the class and illegal outside it, so privacy is enforced by *where you are*. With a constructor,
  privacy is enforced by *what you call* — the outside cannot reach the fields at all, and the
  constructor's contract is the only way in.

### The costs, and one of them is a real risk

- **`__construct` is a name with history, not a neutral one.** It is PHP's, and PHP's is a magic
  method — a name the language treats specially, which this language has otherwise avoided (`#` is
  reserved and unused; `_` is not a wildcard). If it arrives, it should arrive because it is the
  clearest name for a reader who has met PHP, and that should be **stated** rather than absorbed. The
  alternative is a word — `class Account { new(...) }` or `init` — and this is a naming decision worth
  making deliberately once, since it appears in every class anyone writes.
- **A positional constructor re-introduces exactly the transposition hazard §2 is about.**
  `__construct(self.owner, self.balance - amount)` with two `String` fields adjacent is the SAME bug
  as the transposed literal, now with no field names at all to check against. So a constructor does
  not remove the hazard on its own; it needs either named arguments (a papercut row today) or a `with`
  form inside the body. **§3 and §5b compose; neither alone is sufficient**, and that is the finding.
- **Defaulting the return type** (2 above) trades a written promise for brevity, and this language has
  not made that trade elsewhere.

### The order this should be built in

1. **`function (self)` without the type inside a class body** — smallest, purely a refusal to relax,
   and it removes one of the three name repetitions immediately.
2. **`__construct` (or its chosen name), with contracts** — the one door, and where §5a's accessors
   get their rules.
3. **`with`, inside constructor and accessor bodies** — because a positional constructor still has the
   transposition hazard, and this is what removes it.
4. **Named arguments** — from `F` (papercuts), which would make 3 optional rather than necessary.

Which is the answer to the question §5a left open: **not "does §5a subsume §3"**, but that the
constructor is the door, accessors are the rules, and `with` is what keeps either from re-introducing
the bug the whole spec exists to remove.

## 6. Where it does NOT go

- **No `with` on an enum variant.** A variant's payload is positional, so there is no field name to
  key on, and inventing one would be a second way to write a variant.
- **No nested paths** (`with { inner.field: x }`). A record's field is a value; changing something
  inside it is `with { inner: self.inner with { field: x } }`, which is longer and says exactly what
  it does. A path form would hide a copy of `inner`.
- **No conditional fields.** `with { balance: if ... }` waits on `if` as an expression (`M10` §3),
  and this spec does not force that decision.

## 7. What this costs to build

Small, and the shape is known: it is a record literal whose missing fields are filled from another
expression of the same type.

- **Lexer:** `with` becomes a keyword. It is not currently one, so the highlighter, the language
  server's keyword list and the packaged extension all move with it — `M10` §2e is a rule, not a
  courtesy.
- **Parser:** a postfix form after an expression, at the same precedence as a record literal.
- **Checker:** resolve the left side's type, require a record, apply rules 1–6.
- **Codegen:** copy the left side, then overwrite the named fields. No new layout, no new ABI — the
  result is a record built the way records are already built.
- **Both compilers, in the same version**, and a fail fixture per refusal in §4. The `?` operator is
  the cautionary precedent: it shipped in stage-0, no `tests/pass/` fixture used it, and the Burxt
  front end did not implement it *at all* for as long as it existed — invisible because nothing
  compared the two. See `spec/1.0/ROADMAP-1.0.md` §A0d.

## 8. Acceptance

1. `return self with { balance: self.balance - amount };` compiles, in both compilers, and
   `examples/classes.bx` reads with it.
2. A transposed nine-field copy is no longer the shortest way to write a one-field change — measured
   as a fixture that would have been eight hand-copied lines.
3. Five fail fixtures: an unknown field, a field named twice, an empty `with`, a `private` field
   named from outside its class, and a type mismatch on a named field.
4. A pass fixture where the left side is **not** `self`, so the general form is covered rather than
   the motivating case only.
5. A pass fixture where the class has an **invariant** and `with` is checked against it (rule 6),
   because that is what pays for §5.
6. The keyword reaches the highlighter, the language server and the packaged extension in the same
   version.
