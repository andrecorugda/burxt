# Burxt — A4.5 Aggregate ABI Specification

> Status: **spec, to implement.** This defines how multi-field values (records,
> arrays, and — via A4.6 — objects) are laid out in memory and passed across
> function boundaries. It is the substrate the entire OOP model sits on. Getting
> the calls here right is what prevents a codegen rewrite under a finished grammar.
>
> Governing constraint (from the North Star / DESIGN.md): **byte-identical
> observable semantics across all targets.** Mechanism may vary per target;
> *semantics may not.* Every decision below is measured against that.

---

## 0. The one principle that resolves most disputes

**Semantics are defined at the value level; the ABI is a mechanism that must be
invisible to those semantics.**

A Burxt aggregate is a *value*. Passing it, returning it, and assigning it are all
**value-copy** operations, semantically — the callee gets its own logical copy and
cannot observe the caller's storage, on any target. Whether the machine achieves
that by copying two registers or by passing a pointer to a temporary is a target
mechanism the *program can never observe*. If a program could tell the difference,
the ABI is wrong, not the program.

This single rule decides §1 and §2 below. Hold it.

---

## 1. By-value / by-pointer threshold — DECISION: uniform value semantics, varying mechanism

**Your instinct is correct and it is the only choice consistent with the North Star.**
The semantics are uniformly value-copy on every target; the *mechanism* (registers
vs. hidden pointer) varies by target and size, and is unobservable.

Rules:

- **Semantically**, every aggregate pass is a copy. The callee mutating a parameter
  never affects the caller's value, regardless of how it was passed. This is
  identical on x86-64, aarch64, and wasm32.
- **Mechanically**, codegen MAY pass small aggregates in registers and large ones by
  a pointer to a caller-owned temporary. The size threshold is a *per-target*
  detail (e.g. SysV's two-eightbyte rule), chosen for efficiency, never exposed.

### The aliasing trap you named — this is the crux, so it is mandated, not left to care

The danger is exactly what you flagged: by-pointer passing introduces a real pointer
where the semantics promise a copy. A naive implementation lets the callee write
through that pointer and corrupt the caller. **The spec forbids this structurally,
not by discipline:**

- When an aggregate is passed by-pointer as a mechanism, the **caller** allocates a
  fresh temporary, copies the value into it, and passes a pointer to *that*. The
  callee's pointer therefore never aliases the caller's live storage. (LLVM's
  `byval` attribute encodes exactly this contract; use it, don't hand-roll it.)
- The callee treats a by-pointer parameter as **read-owned**: it may read freely and
  may mutate its *local copy*, but that copy is the temporary, not the caller's.
- A by-pointer parameter is therefore semantically indistinguishable from a
  by-register one. **Codegen must be free to switch a given type between the two
  mechanisms with zero source-visible effect.** That freedom is the correctness
  test: if switching the mechanism changes any observable behavior, there is a bug.

> Implementation note: do NOT invent your own by-value-through-pointer lowering.
> Emit LLVM `byval(T)` on the parameter and let the backend honor the platform
> rule. Hand-rolled versions are where the aliasing bugs live.

## 2. Return convention — DECISION: always sret for aggregates (one path)

**Adopt your simpler instinct: always use an sret hidden pointer for aggregate
returns. Do not implement the register-pair path in A4.5.**

Reasoning, weighed honestly:

- **One code path.** Register-pair returns are a per-target size-classification
  problem (which fields land in which registers, how mixed int/float aggregates
  split). Doing it right is real work and it is *per target*. sret is uniform: the
  caller allocates space, passes a hidden pointer as an implicit first argument, the
  callee writes the result there. Identical shape on x86-64, aarch64, wasm32.
- **wasm-friendly.** wasm has no notion of returning a struct in registers at all;
  sret is the natural lowering there anyway. Choosing sret now means the return path
  does not need a wasm-specific rewrite in Phase D.
- **Semantics-preserving trivially.** The returned value is constructed in
  caller-owned space; there is no aliasing question and no copy-elision subtlety to
  get wrong.
- **The cost, stated plainly.** sret can be marginally slower than returning a small
  aggregate in registers, because it forces a memory round-trip. BUT: (a) LLVM's
  optimizer frequently recovers this via return-value optimization / mem2reg when it
  can see both sides, so the real cost is often zero; and (b) Burxt is optimizing for
  *correctness and cross-target uniformity first* — a small, optimizer-recoverable
  return-path cost is exactly the kind of trade the North Star says to make. If
  profiling later shows a hot path where it matters, a register-pair fast path can be
  added *behind* the same semantics as a pure optimization. It is not a v1 concern.

Rule: **scalars (Int, Decimal-as-i64, Bool, pointers) return in a register as today;
every aggregate returns via sret.** The boundary between "scalar" and "aggregate" is
the presence of more than one field / any aggregate type — decided by the type, not
by size, so it too is target-independent.

## 3. Layout — DECISION: layout IS exactly the declared fields, no hidden header, ever

**This is the A4.6-anticipating constraint you asked for, and it must be written
into A4.5 as a hard guarantee, because A4.6's method dispatch depends on it.**

The structs agent's dictionary-passing (fat-pointer) model is adopted as the
forward assumption: **method tables live *outside* the object.** An interface object is a
(data pointer, vtable pointer) pair; the vtable is never embedded in the value. The
consequence for A4.5 is a guarantee that must hold now:

- **The in-memory layout of an aggregate is exactly its declared fields, in
  declaration order, with standard alignment padding between them — and NOTHING
  else.** No type tag, no vtable pointer, no refcount, no hidden header word. What
  you declare is what is laid out.
- **Field offset is a pure function of the declared field types and order.** A
  field's offset never depends on whether the type participates in an interface, how many
  methods it has, or anything discovered later. Adding an interface implementation in A4.6 must not
  move a single field.
- **Alignment:** each field is aligned to its natural alignment; the aggregate's
  alignment is the max of its fields'; total size is rounded up to that alignment.
  This is the standard C-struct rule and it is deterministic per target. (Field
  offsets can differ across targets only via differing scalar alignments, which is a
  mechanism detail; the *field order and logical shape* are identical everywhere, so
  `field N` means the same field on every target — the semantic invariant holds.)
- **No field reordering in v1.** Even though reordering to minimize padding is a
  known optimization, it makes offsets non-obvious and complicates FFI. Keep
  declaration order; revisit as an opt-in optimization later, never as a silent
  default. (Mark as a known-interim in DESIGN.md so it is not mistaken for finished.)

> Why this matters for A4.6: if layout were "fields plus a hidden vtable header,"
> then every offset would shift the moment a type became an interface object, and codegen
> written in A4.5 would break in A4.6. Mandating "layout == declared fields, dispatch
> is external" now means A4.6 adds dispatch *without touching layout*. That is the
> whole point of sequencing A4.5 first.

## 4. Arrays vs records — DECISION: [T; N] passes as (pointer, static length), not as a true aggregate

**Your instinct is right; formalize it.** Arrays and records are both aggregates but
have different shapes, and conflating them is wasteful.

- A `[T; N]` has a **compile-time-known length N** and homogeneous elements. It does
  NOT need the field-by-field aggregate machinery.
- **Passing:** an array parameter lowers to a **pointer to the elements plus a
  static, compile-time length N** carried in the type — not copied element-by-element
  onto the stack as a monolithic aggregate. Because N is a compile-time constant, the
  length travels in the *type*, not as a runtime argument.
- **Semantics unchanged:** it is still a value-copy semantically (§0). If the callee
  needs to mutate without affecting the caller, the caller-temp rule from §1 applies —
  a fresh copy of the N elements. The pointer-plus-length is a *mechanism*; the copy
  semantics are preserved.
- **Distinction from records:** records pass per §1 (byval mechanism, heterogeneous
  fields); arrays pass as pointer+static-N. Keep the two lowerings separate in
  codegen so neither is forced into the other's shape.
- **Forward note:** dynamically-sized sequences (a future `List<T>` / slice) are a
  *different* type from `[T; N]` and will carry a runtime length. Do not build A4.5's
  fixed-array lowering in a way that assumes it will generalize to dynamic length;
  that is a Phase A4.4-collections concern with its own ABI.

## 5. What A4.5 must deliver (implementation checklist)

Concrete, in dependency order:

1. **Layout computer.** A function `layout_of(Type) -> { size, align, field_offsets }`
   implementing §3 exactly: declared fields, standard alignment, no hidden header.
   Deterministic and target-parameterized only through scalar alignments.
2. **Aggregate LLVM type mapping.** Map a Burxt aggregate to an LLVM struct type
   whose element order/types match §3 one-to-one. No extra elements.
3. **Parameter lowering.** Scalars in registers; aggregates via `byval(T)` with the
   caller-temp guarantee (§1); arrays as pointer + static length (§4).
4. **Return lowering.** Scalars in a register; **all aggregates via sret** (§2):
   allocate in caller, pass hidden pointer, callee writes through it.
5. **Copy semantics enforcement.** Every pass/return/assign of an aggregate is a
   value-copy; verify by a test that mutating a passed aggregate never affects the
   caller, across a by-register type AND a by-pointer type (§1's correctness test).
6. **The mechanism-switch test.** A test that forces the same aggregate type through
   both mechanisms (e.g. by size manipulation or a codegen flag) and asserts
   identical observable behavior. This is the guard that §1/§2 stay honest.

## 6. What A4.5 must NOT do (scope discipline)

Per the North Star's kitchen-sink rule — these are explicitly out, to keep the ABI
minimal and prevent it absorbing later phases:

- **No method dispatch.** That is A4.6. A4.5 only guarantees the layout that makes
  external dispatch possible.
- **No register-pair return fast path.** sret only (§2). Add later as pure
  optimization if profiling demands, never as a semantic variant.
- **No field reordering / padding optimization.** Declaration order only (§3).
- **No dynamic-length sequences.** `[T; N]` only; `List<T>`/slices are later (§4).
- **No FFI struct-compat layer yet.** A4.5 defines *Burxt's* ABI. Matching the C ABI
  for FFI is A3/FFI's concern and can layer on top; do not entangle them here.

## 7. Superseded / interim ledger (append to DESIGN.md, do not swap silently)

- **Register-pair returns: superseded by sret** for v1 (§2). Recorded as a
  deliberate simplicity-over-peak-performance choice, reversible as an optimization
  behind unchanged semantics.
- **Field reordering: known-interim.** Declaration-order layout is intentional for
  now; padding-minimization deferred, not forgotten.
- **These join the existing known-interim entries** (512 MB compile stack with the

## 8. The forward-guarantee summary (what A4.6 is allowed to assume)

When A4.6 builds composition-first OOP on top of this, it may rely on exactly these,
and no more:

1. An aggregate's layout is its declared fields, in order, standard alignment, **no
   hidden header** — so trait participation never moves a field.
2. Dispatch data lives **outside** the value (fat-pointer / dictionary model); the
   value itself is pure data.
3. Passing/returning/assigning an aggregate is a **value-copy** on every target;
   mechanism is invisible.
4. `field N` denotes the same logical field on every target.

If A4.6 ever needs to violate one of these, that is a signal to revisit A4.5
deliberately and record it in the ledger — not to bolt a hidden header onto the
layout and hope.
