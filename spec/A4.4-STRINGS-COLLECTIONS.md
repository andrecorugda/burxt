# Burxt — A4.4 Strings & Collections Specification

> Status: **spec, to implement.** Adds the data types real programs need: proper
> strings and sequences. Moderate design risk — the memory-ownership question lurks
> here (dynamic collections need heap allocation), so this spec deliberately scopes
> to what can be built BEFORE the borrow model, and flags what must wait for it.

## 0. The ownership caveat up front
Dynamic, growable collections (a `List<T>` that can grow) need heap allocation and
therefore an answer to "who frees this / when." That answer is the memory model
(a later, big milestone). So A4.4 is split:
- **What ships now**: `String` (immutable), fixed-size arrays `[T; N]` (already
  partially present), and read operations. These can use simple, safe allocation
  strategies (immutable, copied, or arena) without the full borrow model.
- **What waits**: growable `List<T>`, mutation of collections, slices with
  lifetimes. These are flagged for the memory-model phase.

## 1. Strings
- **`String` is an immutable, UTF-8 sequence of bytes.** Decide this now and hold it:
  strings are UTF-8, always. No implicit encoding conversions (the Python-2→3 lesson).
- String literals: `"hello"`, with escapes (`\n`, `\t`, `\"`, `\\`).
- **String vs bytes are separate types.** A `String` is text; raw `Bytes` (if/when
  added) is separate. No implicit mixing. (Deferred: Bytes type — trigger: binary I/O.)
- Operations in A4.4: length, equality (same-type, per correctness family),
  concatenation (produces a new String — immutable), indexing by... **flag**: byte
  index vs char index is a real decision. Recommendation: index returns are explicit
  (`.bytes()` vs `.chars()` views) rather than a bare `s[i]` that hides the
  byte/char ambiguity. Keep bare indexing OUT until decided; expose explicit views.
- Interpolation (from A4.7) builds Strings.

## 2. Fixed arrays `[T; N]`
- Compile-time-known length N, homogeneous elements. Already partially present per
  A4.5 (passed as pointer + static length).
- A4.4 formalizes: construction (`[1, 2, 3]` or `[0; N]`), indexed read `a[i]` with
  **bounds handling** — out-of-bounds is a trap, never undefined behavior (correctness
  family: no reading garbage). Compile-time-constant indices can be bounds-checked at
  compile time; runtime indices get a runtime bounds check.
- Iteration: with A5.0's `while` and an index, arrays are iterable manually. `for`
  sugar waits for the iterator protocol (deferred).

## 3. What A4.4 must NOT do (deferred, triggers)
- **NO growable `List<T>`.** Needs heap + ownership answer. Trigger: memory model phase.
- **NO collection mutation** beyond fixed-array element assignment to a `mut` binding.
- **NO slices/views with lifetimes.** Needs borrow tracking. Trigger: memory model.
- **NO maps/dictionaries.** Need hashing + growable storage. Trigger: after List<T>.
- **NO `for` loops / iterator protocol.** Trigger: after growable collections make
  iteration general. `while` + index suffices now.
- **NO bare string indexing `s[i]`** until byte-vs-char is decided — use explicit
  `.bytes()`/`.chars()` views. Prevents the silent-wrong-index class of bug.
- **NO string mutation.** Strings are immutable in A4.4; mutable string building
  (a `StringBuilder`) waits for the memory model.

## 4. Deliverables
1. `String` type, UTF-8, literals with escapes, immutability.
2. String length, same-type equality, concatenation (new String).
3. Explicit `.bytes()` / `.chars()` views instead of bare indexing.
4. `[T; N]` construction, bounds-checked indexed read, `mut`-element assignment.
5. Compile-time bounds check for constant indices; runtime trap for dynamic OOB.
6. Tests, rejection-weighted:
   - string build/concat/interpolate correctly; UTF-8 preserved;
   - array construct/read/write; **rejections**: OOB constant index (compile error);
     OOB runtime index (trap with message); cross-type string comparison; bare `s[i]`
     (rejected, pointed to `.bytes()`/`.chars()`); mutating a non-`mut` array.

## 5. The honest note
A4.4 intentionally delivers the *immutable, statically-sized* half of data handling
and stops at the heap boundary. This is not timidity — it is refusing to build
growable collections on an ownership model that does not exist yet, which would force
either a GC decision or unsound manual memory handling. The line is drawn exactly at
"needs a heap answer." Everything past that line is the memory model's job.
